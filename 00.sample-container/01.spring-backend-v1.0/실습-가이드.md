# 주문 관리 시스템 실습 가이드

기존 User / Product CRUD 코드를 기반으로 **주문(Order) → 결제(Payment) → 배송(Delivery)** 흐름을 직접 구현하는 실습입니다.  
이 가이드는 "무엇을 만들어야 하는지"를 중심으로 작성되었습니다. 세부 구현은 기존 코드를 참고하여 스스로 작성해 보세요.

---

## 1. 최종 목표 모습

- 사용자는 상품 목록에서 상품을 선택해 **주문**할 수 있다.
- 주문이 생성되면 상태가 **주문 완료** 로 시작하고, 클릭할 때마다
  **주문 완료 → 결제 대기 → 결제 완료 → 배송 대기 → 배송 완료** 순서로 진행된다.
- 결제 완료 시점에 결제(Payment) 정보가, 배송 완료 시점에 배송(Delivery) 정보가 완료 처리된다.
- Thymeleaf 화면(상품 관리, 사용자 관리, 주문 관리)은 `03.frontend` 프로젝트에서 별도로 실행하며, 이 프로젝트(01)의 REST API를 호출해 화면을 구성한다.
- REST API(Swagger UI)로도 동일한 기능을 호출할 수 있다.

## 2. 주요 적용해야 할 기술

| 기술 | 어디에 쓰는가 |
|---|---|
| JPA 연관관계 `@ManyToOne` | 주문 → 사용자, 주문 → 상품 연결 |
| JPA 연관관계 `@OneToOne` | 주문 → 결제, 주문 → 배송 (주문 저장 시 함께 저장) |
| `@Enumerated(EnumType.STRING)` | 주문/결제/배송 상태를 문자열로 저장 |
| Enum에 메서드 정의 | `next()` 로 다음 상태 계산, `getLabel()` 로 한글 표시 |
| `@Transactional` + 변경 감지(dirty checking) | 상태 전환 시 save 호출 없이 자동 반영 |
| Spring Data JPA 쿼리 메서드 | `findByNameContaining` (검색), `findByUserId` |
| Thymeleaf | `th:each`, `th:if`/`th:unless`, `@{...}` URL, 폼 전송 |
| `@Controller` vs `@RestController` | 화면 컨트롤러와 API 컨트롤러 분리 |

## 3. Entity 목록과 역할

### Order (주문) — 핵심 엔티티
- 역할: 사용자가 상품을 주문한 1건을 표현하고, 전체 진행 상태를 관리한다.
- 속성(도메인 관점):
  - 주문한 **사용자** (N:1)
  - 주문한 **상품** (N:1)
  - **수량**
  - **진행 상태** (주문 완료 / 결제 대기 / 결제 완료 / 배송 대기 / 배송 완료)
  - **주문 시각**
  - **결제 정보** (1:1), **배송 정보** (1:1)

### Payment (결제)
- 역할: 주문 1건의 결제 금액과 결제 여부를 관리한다. 주문 생성 시 함께 생성된다.
- 속성: 결제 **금액**(가격 × 수량), 결제 **상태**(대기/완료), 결제 **완료 시각**

### Delivery (배송)
- 역할: 주문 1건의 배송지와 배송 여부를 관리한다. 주문 생성 시 함께 생성된다.
- 속성: **배송지 주소**, 배송 **상태**(대기/완료), 배송 **완료 시각**

### 기존 엔티티
- User (사용자): 이름, 이메일 — 주문의 주체
- Product (상품): 상품명, 가격, 재고 수량, 판매 상태 — 주문 대상 (주문 시 재고 차감)

### 상태 Enum
- `OrderStatus`: ORDER_COMPLETED → PAYMENT_PENDING → PAYMENT_COMPLETED → DELIVERY_PENDING → DELIVERY_COMPLETED
- `PaymentStatus`, `DeliveryStatus`: PENDING / COMPLETED

## 4. API 목록과 설명

### 주문 API (`/api/orders`)
| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/orders` | 전체 주문 조회 |
| GET | `/api/orders/{id}` | 주문 단건 조회 |
| GET | `/api/orders/user/{userId}` | 사용자별 주문 조회 |
| POST | `/api/orders` | 주문 생성 (productId, userId, quantity, address) |
| POST | `/api/orders/{id}/next-status` | 상태를 다음 단계로 전환 |
| DELETE | `/api/orders/{id}` | 주문 삭제 (결제·배송도 함께 삭제) |

### 결제 API (`/api/payments`)
| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/payments` | 전체 결제 조회 |
| GET | `/api/payments/{id}` | 결제 단건 조회 |
| POST | `/api/payments/{id}/complete` | 결제 완료 처리 |

### 배송 API (`/api/deliveries`)
| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/deliveries` | 전체 배송 조회 |
| GET | `/api/deliveries/{id}` | 배송 단건 조회 |
| POST | `/api/deliveries/{id}/complete` | 배송 완료 처리 |

### 화면 URL (Thymeleaf, `03.frontend`에서 제공)
| 경로 | 화면 |
|---|---|
| `/` | 메인 메뉴 |
| `/view/products` | 상품 검색/등록/삭제 |
| `/view/users` | 사용자 검색/등록/삭제 |
| `/view/orders` | 상품 목록(주문 버튼) + 주문 목록(상태 버튼) |
| `/view/orders/new?productId=N` | 사용자 선택 후 주문 확정 |

> 위 화면들은 이 프로젝트(01)가 아니라 `03.frontend` 프로젝트를 실행했을 때 제공된다. 자세한 내용은 `03.frontend/README.md` 참고.

## 5. 사용자 시나리오 (API 연결 흐름)

### 시나리오 1: 상품/사용자 준비
1. 상품 관리 화면에서 상품 등록 → `POST /view/products` (API: `POST /api/products`)
2. 사용자 관리 화면에서 사용자 등록 → `POST /view/users` (API: `POST /api/users`)

### 시나리오 2: 주문 생성
1. 주문 관리 화면 진입 → 상품 목록 표시 (`GET /view/orders`)
2. 상품의 [주문] 버튼 클릭 → 사용자 선택 화면 (`GET /view/orders/new?productId=1`)
3. 사용자·수량·배송지 입력 후 [주문 확정] → `POST /view/orders` (API: `POST /api/orders`)
   - 서버 내부: 재고 차감 → Payment(결제 대기)·Delivery(배송 대기) 생성 → Order(주문 완료) 저장
4. 주문 목록에 **주문 완료** 상태로 표시됨

### 시나리오 3: 상태 전환
1. 주문 목록에서 상태 버튼 클릭 → `POST /view/orders/{id}/next` (API: `POST /api/orders/{id}/next-status`)
2. 클릭할 때마다: 주문 완료 → 결제 대기 → **결제 완료**(이때 Payment도 완료 처리) → 배송 대기 → **배송 완료**(이때 Delivery도 완료 처리)
3. 배송 완료 후에는 더 이상 상태가 바뀌지 않는다.

### 확인 방법
- Swagger UI: `http://localhost:8080/swagger-ui.html`
- H2 콘솔: `http://localhost:8080/h2-console` (orders / payments / deliveries 테이블 확인)

## 6. 구현 순서 제안

1. 상태 Enum 3개 작성 (`OrderStatus`, `PaymentStatus`, `DeliveryStatus`)
2. `Payment`, `Delivery` 엔티티 작성 (연관관계 없는 단순 엔티티부터)
3. `Order` 엔티티 작성 (`@ManyToOne` 2개, `@OneToOne` 2개 + cascade)
4. Repository 3개 작성
5. `OrderService` 작성 — 주문 생성 로직과 상태 전환 로직이 핵심
6. `PaymentService`, `DeliveryService` 작성
7. REST Controller 3개 작성 → Swagger로 테스트
8. `03.frontend` 프로젝트에서 Thymeleaf 화면 작성 (상품 → 사용자 → 주문 순서)
